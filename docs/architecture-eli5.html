ReviewPilot：56 个类是怎么打配合的

把一份 GitHub PR 变成一份代码审查报告。中间是一条 7 站的传送带： 前 4 站是「死规矩」（代码写死的，永远给同样答案）， 后 3 站是「活脑子」（会调用大模型，每次结果可能不同）。

确定性层 · 可预测 Agent 层 · 会自己查资料 质检层 · 挑毛病返工 数据盒子 · 在站间传递

02 · 备料四站（确定性，可单测）

跑腿员

「去 GitHub 把改动取回来」
GithubPrFetcher · 66 行 HTTP 装配
它做
发 API 拿 PR 的 files / title / 代码搜索结果；把 404/401/403 翻译成 3 种自己的异常
交给
DiffParser —— 边拉边拆，产出 FileChange
还服务
ToolRegistry（searchCode）、FileContentFetcher、PrFilesController

翻译员

「把一坨文本变成一行一行」
DiffParser · 纯函数，不联网
它做
正则认 @@ 头，逐行按前缀分派，维护新旧两个行号计数器
狠处
遇到未知前缀 直接丢掉整个 hunk（宁可少报，不许行号错位）
暗号
行号 0 = 这行不存在。新增行 old=0，删除行 new=0 —— 下游全靠前几过滤

分拣员

「这是测试、那是 SQL」
FileClassifier → FileType
它做
看路径 + diff 片段，5 级优先：TEST→SQL→CONFIG→JAVA→OTHER；没注解就回退看后缀
谁听
9 个风险规则（决定我该不该检查这文件）+ PromptBuilder（分组）
别扭
risk 包依赖 classifier 包的枚举 —— 改枚举，9 个规则一起受影响

9 个检查员

「每人只管一条死规矩」
RiskDetector + RiskRule × 9
契约
id() / appliesTo(FileType) / scan(FileChange)→List<RiskItem>
调度
Spring 把 9 个 @Component 注成 List<RiskRule>，双层循环全问一遍
没有
无优先级、无短路、无去重；某条规则炸了只 WARN，不中断
加规则
丢一个类进 rules/ 就行，注册中心不用改

剪裁员

「给出事那行旁边几行」
ContextLoader → ContextSlice
它做
从已有的 hunks 里裁 ±5 行，相邻窗口合并
关键
它不联网（源码里明确注释）。全文是另一个人的活

取全文的

「把整份文件搬回来」
FileContentFetcher
两个门
fetchForRiskyFiles() ← 只有工头用（批量预取，受开关控制）
fetchContent() ← 只有 ToolRegistry 用（模型主动要）
重复
两边都会各发一次 PR metadata 请求，head ref 被反复取，无缓存

03 · 站 5：ReviewAgent 的循环（整个项目最聪明的一段）

1
先算字数 对话超 80%（64000 字符）→ 把超过 2000 字的工具结果砍到 1000；超 100% → 直接逼模型收尾，不再给它选
2
决定这次给不给工具 已经调过 4 次工具就把工具收走 —— 防止模型无限查下去，逼它收敛
3
问大脑 modelProvider.chat(messages, tools) → 拿回 AgentResponse
4
有 tool_calls？ 先把模型这句话塞回历史，再逐个 toolRegistry.execute(call, pr)，结果包成 Message.tool() 追加；第 3 次起额外插一句中文「别再查了」
5
没 tool_calls → 这就是终稿 parseWithRetry()：剥代码围栏 → 抽 JSON → 解析。失败就把报错原文塞回去再问一次；还失败 → 退化成正则抠 summary，风险列表交空（只记日志，不报错）
↺ 回到 1。轮数上限 max-rounds: 8；第 0 轮就想退出会被判定异常，走 forceComplete。 跑完 lastReactRounds / lastToolCallCount 被工头反读，塞进响应的 Meta。

04 · 工具箱和大脑（Agent 的两个外部件）

工具箱

「模型的手」
ToolRegistry · 线程安全单例
两个工具
fetch_file_content(path)search_repo(query)
怎么注册
硬编码在 getDefinitions() 里的 List.of(...)，不扫注解 —— 加工具 = 改这个方法
怎么分发
switch(call.name())，default 返回「Unknown tool」；所有异常被包成字符串，工具永远炸不掉循环
限流
只有 search_repo：固定窗口 25 次/60s（AtomicInteger + volatile），加 ConcurrentHashMap 缓存，键 owner/repo/query，永不淘汰且跨 PR 共享
巧处
PrUrl 是方法参数不是字段 —— 单例才不会被打上某个 PR 的状态

大脑插座

「换大脑不用改电路」
ModelProvider（接口）← DeepSeekProvider（唯一实现）
两个方法
complete(sys,user) 单发无记忆 · chat(messages,tools) 多轮带工具
谁在用
同一个 bean 被 3 处注入：ReviewAgent(用 chat)、ReflectionOrchestrator(用 complete)、ReviewPipeline(用 complete)
HTTP
WebClient + .block()（响应式壳，同步芯）。DeepSeekClientConfig 造，带 @Qualifier —— 因为 GitHub 那边也造了一个 WebClient，同类型两个 bean 不指定会歧义
重试
只重 连接被重置/超时/拒绝 这类；4xx/5xx 立刻抛，不浪费重试

写说明书的

「决定模型看见什么」
PromptBuilder(bean) + PromptTemplate(enum)
分工
Builder 管全部文案和字数预算（单文件 6000 字 / 总 60000 字）与截断；systemPrompt() 里是 8 条 ## Rule N 审查员守则，reactSystemPrompt() 只是「8 条 + 一段 Tool Use」。Template 只是 FileType → 提示语 的静态映射，不是 bean
谁调
ReviewAgent 要 reactSystemPrompt()；ReviewPipeline 要 systemPrompt()+build()
代价
一次请求把 user prompt 造了两遍，而且内容不同：Agent 那份不带 fullFileContents（要它自己用工具去取），质检/返工那份带 —— 于是返工看到的材料比原审查还多。系统提示词那半边是故意的、没问题

05 · 站 6：质检环（一个很克制的实现）

1
换个身份再问一次 同一条 complete()，但系统提示词换成「你是质检员」。查 5 类毛病：
[HALLUCINATION] 编的[MISSING] 漏的[SEVERITY] 判级错[DUPLICATE] 重复[CONSISTENCY] 前后矛盾
2
要不要返工 needsRevision() = !issues.isEmpty() —— 故意不打分数，有问题就返工，语义简单
3
返工 = 重新生成一次 把毛病追加进系统提示词，再 complete() 一次。不重跑 ReviewAgent
⚠ 质检和返工都走 complete() —— 所以它们没有工具、没有多轮历史：只能就着已有材料挑毛病，不能自己去 GitHub 查证是否编造。 返工只 1 次（配置里写的 2 被注释掉了）。质检自己的回答解析失败会重试 1 次，再失败就记 ERROR 并放行原稿，不静默吞掉。

06 · 谁被塞进谁（构造器注入的真图）

前台层
ReviewController ── ReviewPipeline （只此一个，不认识任何 AI 类）
PrFilesController ── GithubPrFetcher · HealthController ── （零依赖）

工头（9 个依赖，全场最大扇出）
ReviewPipeline ──┬─ GithubPrFetcher ├─ FileClassifier ├─ RiskDetector
                   ├─ ContextLoader ├─ FileContentFetcher
                   ├─ ReviewAgent ├─ PromptBuilder
                   ├─ ReflectionOrchestrator └─ ModelProvider (工头自己也要单发一次)

往下就三根线
ReviewAgent ── ModelProvider · ToolRegistry · PromptBuilder
ToolRegistry ── GithubPrFetcher(searchCode) · FileContentFetcher(fetchContent)
ReflectionOrchestrator ── ModelProvider （只用到 complete，不碰工具）
RiskDetector ── List<RiskRule> ×9 · FileClassifier （↖ 跨层依赖，见下方残留）

数据盒子（谁写 → 谁读）
FileChange 全场主干 → .hunks() 喂 9 规则 + ContextLoader ｜ .patch() 只有 FileClassifier 读 ｜ .binary() 只有 PromptBuilder 与 HardcodedSecretRule 读
RiskItem → RiskDetector 与 ReviewAgent 两边产 → PromptBuilder · Critic · mergeRisks · 前端 JSON
PrUrl → 前台 parse() 一次 → 之后一路当参数往下传（不做字段、不做 ThreadLocal）

07 · 出货前的合并

怎么去重
mergeRisks() 在工头里（private static）。键是 file|line|message 三段全等，装进 LinkedHashSet
谁赢
规则风险先进，AI 风险后进 —— 模型复述了同一条会被吃掉；但换了措辞就留下两行（无排序、无按 severity 合并）。这个漏网之鱼正是质检 [DUPLICATE] 要抓的

08 · 重构留下的痕迹（诚实清单）

V3 把「单次调用」改成了 ReAct，搬得很干净的地方是 service/ai；下面这几处是搬完还挂在外面的。

两套几乎一样的 JSON 解析栈 ReviewAgent 和 ReviewPipeline 各有 parseWithRetry / parseCleaned / parseRisks / parseSuggestions。只把剥围栏抽成了 JsonReplyCleaner。原因：返工输出的解析还留在工头（V2 时代写的），没跟着搬。
工头里有一段死代码 ReviewPipeline.parseModelReply() 在主代码里没有任何调用方，只有 ReviewPipelineParseTest 在用 —— 测试在保着一份没人跑的旧逻辑。
同一份 user prompt 造两遍，内容还不一样 工头 :133 造的那份带全文，只在触发返工时才被用 —— 不触发就是白算。而 ReviewAgent 走 reactUserPrompt()，它内部转调 build(..., Map.of(), ...)，不带全文（要求模型自己用工具取）。结果：返工拿到的材料比被它修正的那份审查还多。系统提示词那半边是故意的：reactSystemPrompt() = 基础 8 条守则 + 工具段落，返工没工具所以正好该丢掉那段。
分类做了两遍 工头 :108 对全部文件分类一次，RiskDetector:43 又对同一批 FileChange 分一次。FileClassifier 无缓存。
类型过滤有两条不一致的路 9 条规则里 7 条覆盖 appliesTo()；BareCatch 和 ExceptionSwallowing 用默认 true，改在 scan() 里 filename.endsWith(".java") 兜底。同一个判断两个地方做。
keyFindings 在返工时丢了 只有 ReviewAgent 的解析器认 keyFindings，工头那份不认 → 一旦触发返工，这个字段静默变空。
Agent 用可变字段往外递统计 lastReactRounds / lastToolCallCount 是单例 bean 上的可变字段，工头跑完再反读 —— 并发请求会互相覆盖。
ToolCall.mapToJson 手搓 JSON 不转义 StringBuilder 拼的，参数里出现 " 或换行就生成非法 JSON —— 而这段正好会在第 2 轮起被重放进对话历史。
HTTP 状态码靠字符串嗅探 工头/前台判断「是不是没配 key」用的是 message.startsWith("DeepSeek API key is not set") 决定回 401 还是 502。改文案就断。
5 个死字段 + 一处冗余取数 GithubPrFile 的 blobUrl/rawUrl/contentsUrl/sha/changes 全代码零消费（toFileChange 只取 5 个）。而 fullFileContents 是工头预取的，只有返工那份 prompt 用得上 —— ReAct 会自己用 fetch_file_content 再下一遍，预取的那份对主路径是浪费。
不是类协作、但顺手查出来的真 bug：application.yml 的 agent 段是死的 yml 把 react.max-rounds 等 4 个键挂在 reviewpilot.ai.agent.* 下，而代码里 @Value 读的是 reviewpilot.agent.* —— 少了中间那段 .ai，全库只有一个配置文件，所以这 4 个全部落到代码默认值。现在看不出来是因为默认值和文件里写的刚好一样（8 / 64000 / true / true）。真去把 reflection.enabled 改成 false，反射照样会跑。
