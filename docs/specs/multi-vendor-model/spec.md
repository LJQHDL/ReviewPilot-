# 多厂商模型层 需求文档

## 背景

当前项目的 AI 模型层只支持 DeepSeek 一家：模型服务的地址、密钥、模型名等参数被写死在 `reviewpilot.ai.deepseek.*` 这一段配置里，服务启动时据此构造唯一一个调用客户端，之后所有模型调用都走它。

要切换到另一家厂商，需要改代码——因为客户端与 DeepSeek 强绑定。而实际上市面上大多数模型网关都对外提供**同一套 OpenAI 兼容的对话补全接口**（DeepSeek、OpenAI、Kimi、Qwen、GLM、Groq、Ollama、vLLM、SiliconFlow 等），只是地址、密钥、模型名不同。

本次要把「用哪家模型」从**代码决定**变成**配置决定**：运维人员在配置文件里声明若干候选端点、指定其中当前生效的一个，服务即按该端点调用；换厂商不改代码。

> 说明：更长期的目标是「上线后由登录用户在前端各自配置密钥」。那是后续独立子项目（涉及登录、凭证存储、运行时注入）。本次只做模型层的地基——多厂商可配置化，仍由服务端配置管理密钥。本次的设计要为「将来把密钥来源从服务端配置改为运行时注入」留下不返工的扩展空间。

## 目标

- 运维通过配置即可声明多个候选模型端点，并指定当前生效的一个。
- 切换到任意 OpenAI 兼容厂商：只改配置、重启，零代码改动。
- 仓库自带一份开箱即用的默认端点配置（DeepSeek），本地 clone 后即可启动运行。
- 配置错误在启动时即被发现并清晰报错，而不是拖到第一次评审请求。

## 功能需求

- **F1 — 多端点声明：** 系统允许运维人员声明任意数量的、具名的模型端点；每个端点至少包含：服务地址、密钥来源、模型标识，以及可选的生成参数（超时、最大输出 token、温度、重试次数）。
- **F2 — 指定生效端点：** 系统允许通过配置指定其中恰好一个端点为「当前生效」。
- **F3 — 生效端点的确定规则：** 启动时确定生效端点：若显式指定了「当前生效」，用之；若未指定但只声明了一个端点，则该端点自动生效；若未指定且声明了多个，则视为配置错误。
- **F4 — 全链路统一使用生效端点：** 评审流程中所有模型调用（自主探索阶段与质检/修订阶段）都通过当前生效端点发出。
- **F5 — 结果可追溯厂商：** 评审结果中报告本次是由哪个具名端点、哪个模型提供的服务，便于前端展示与排障。
- **F6 — 启动期配置校验：** 系统在启动时校验配置并对以下情况**快速失败并给出明确原因**：生效端点名指向一个未声明的端点、缺少端点关键字段、按 F3 规则无法唯一确定生效端点。错误发生在启动阶段，而非首次调用。
- **F7 — 密钥只来自环境变量、日志脱敏：** 端点密钥的实际值通过环境变量注入（配置文件里只写占位引用），配置文件与代码中不出现明文密钥；任何日志输出只呈现密钥的脱敏形式。
- **F8 — 缺密钥时的降级行为：** 当生效端点的密钥未配置时，评审主接口返回一个明确的鉴权类错误，服务其余部分（健康检查、仅解析 diff 的接口）仍能正常启动与工作；不因缺密钥而导致服务无法启动。
- **F9 — 统一采用 OpenAI 兼容协议：** 对所有端点，模型调用都遵循 OpenAI 兼容的对话补全约定（含多轮消息与工具调用的请求/响应结构）；新增一家同样遵循该约定的厂商无需新增代码。
- **F10 — 预留运行时注入的扩展出口：** 模型层对外暴露一个稳定的调用出口；发起一次调用所需的**端点信息（地址、密钥、模型标识等）经由该出口传入，而非在调用方内部固定获取**。本次该出口从服务端配置取默认生效端点填充；将来把来源改为「运行时/每请求注入」时，仅替换填充来源即可，评审流程等调用方代码无需改动。此出口是后续子项目（登录 + 用户自带密钥）的接入点。

## 非功能需求

- **N1 — 零代码扩展：** 只要厂商满足 F9 的协议约定，接入它不需要改动程序代码。
- **N2 — 行为不回退：** 端点各自的超时、重试等参数被实际遵守，评审时延与稳定性不劣于现状。
- **N3 — 架构边界不破：** 重构后既有的分层依赖约束（下层不得反向依赖上层、流水线层不引入 Web/JSON 库依赖）仍然成立，相关校验测试通过。
- **N4 — 配置简洁：** 采用单一的新配置结构，不为兼容旧配置保留额外分支（当前为个人开发项目，无真实存量用户，本地能启动能跑即可）。

## 不做的事

- 不实现 OpenAI 兼容之外的原生协议适配器（如 Anthropic Messages API、Google Gemini 原生协议）。
- 不做登录、用户体系、凭证的加密持久化存储。
- 不做「运行时随单次请求携带/切换用户密钥」以及前端设置密钥的界面——本次密钥仍由服务端配置统一管理。
- 不做一次评审内同时使用多家厂商。
- 不做不重启即热切换生效端点。
- 不做对旧 `reviewpilot.ai.deepseek.*` 配置形态的向后兼容/自动迁移——直接改用新结构，由仓库自带配置保证本地开箱可跑。
- 不改动 GitHub 抓取层的密钥来源（本次聚焦模型层；GitHub token 的同构改造另议）。

## 验收标准

- **AC1（对应 F1/F2）：** 在配置中声明两个不同地址/密钥/模型的具名端点，并指定其一为生效；服务能成功启动，不报冲突。
- **AC2（对应 F3）：** 不指定「当前生效」但只声明一个端点时，该端点被自动采用；不指定而声明多个端点时，服务启动失败并给出「无法唯一确定生效端点」的明确原因。
- **AC3（对应 F4）：** 触发一次完整评审后，可观测到自主探索与质检两阶段的模型请求都发往生效端点声明的地址（例如通过把生效端点地址指向本地测试服务并捕获到请求来验证）。
- **AC4（对应 F5）：** 评审结果中包含生效端点的名称与模型标识，且与实际配置一致。
- **AC5（对应 F6）：** 将生效端点名设置为一个未声明的名字、或删去某端点必填字段，服务启动即失败并打印可定位的配置错误原因；错误发生在启动阶段而非首次请求。
- **AC6（对应 F7）：** 检索配置文件与代码，无明文密钥；启动日志与错误日志中密钥仅以脱敏形式出现。
- **AC7（对应 F8）：** 生效端点密钥环境变量留空时启动服务：健康检查接口正常返回；调用评审接口返回明确的鉴权类错误；服务进程不因缺密钥而崩溃退出。
- **AC8（对应 F9/N1）：** 将生效端点配置为一个非 DeepSeek 的 OpenAI 兼容端点（如把地址指向本地模拟的 OpenAI 兼容服务），不改任何代码即可发起评审并得到结构化结果。
- **AC9（对应 N4）：** 仓库自带的默认 yml 只含新结构、不含旧 `deepseek.*` 段；本地 clone 后仅设置生效端点的环境密钥变量即可 `mvn spring-boot:run` 启动并完成一次评审。
- **AC10（对应 F10）：** 存在一个明确的调用出口，端点信息由其入参携带；评审流程调用模型时不直接读取配置或持有单一客户端单例，而是经此出口发起——即调用方与「端点来源」解耦（通过代码走查/一个替换填充来源即可切换端点的测试验证）。
- **AC11（对应 N3）：** 分层依赖校验测试与全部既有测试通过。
