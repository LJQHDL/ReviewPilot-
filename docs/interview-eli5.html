01 / 先会讲用途

面试开场，先讲这段

ReviewPilot 是一个 GitHub PR 智能审查助手。前端用 Vue 3，后端用 Spring Boot。后端先解析变更，通过文件分类和 9 条规则定位风险，再让大模型按需读取文件、搜索仓库，生成结构化建议。最后通过 Critic 复核、可选修订和规则结果合并，提高审查结果的完整性。核心设计是规则、上下文和模型推理的协作；当前实现仍有大 PR 覆盖和并发统计等边界。

这段介绍的是项目。面试时再补充你确实负责的模块、遇到的问题和验证过程；个人贡献不能从仓库推断。

02 / 记住这张图

一个后端，协调两种外部能力

架构定位：前后端分离、同步请求、后端分层编排。代码中没有数据库、消息队列、向量库或审查历史存储。

技术栈该怎么解释？

Vue 3 + Element Plus 展示风险；Axios 调接口。Java 17 + Spring Boot 提供 REST 服务。WebClient 调 GitHub 和 DeepSeek，但调用处使用 .block()，所以主链路仍同步等待。Jackson 处理 JSON；ModelProvider 隔离模型调用，当前实现是 DeepSeekProvider。

开发环境 Vite 将 /api 代理到后端 8080。API Key 由后端环境变量读取，浏览器不直接持有模型密钥。

→
④ 查证AI + 工具

⑤ 交报告复核 + 合并
展开：每一步的输入、输出、源码位置
步骤做什么关键实现
接收POST /api/review，校验并解析 prUrlReviewController → PrUrl → ReviewPipeline
抓取 / 解析GitHub patch → FileChange / DiffHunk / DiffLine；区分新增、删除、上下文与新旧行号GithubPrFetcher → DiffParser
分类Controller / Service / Config / SQL / Test / Other；按类型给不同审查关注点FileClassifier / PromptTemplate
规则检测针对适用文件运行 9 条启发式规则，输出 RiskItemRiskDetector / RiskRule
补上下文从已有 hunks 取风险行附近 ±5 行并合并窗口；取不到的代码不会凭空补齐ContextLoader
主动审查标题、diff、分类、风险、局部上下文 → 模型与工具循环 → 初稿PromptBuilder / ReviewAgent / ToolRegistry
复核 / 修订规则风险 + AI 风险与建议 → Critic；有问题则调用模型修订一次ReflectionOrchestrator
合并 / 返回规则先入结果，AI 后入；按 file、line、message 精确去重RiskMerger → ReviewPipeline → ReviewResult

注意：Pipeline 会预取风险文件全文，但没有传给初始 ReviewAgent；它进入后续修订用的 userPrompt。初审要看全文，靠工具另取。

用一个例子串起来

假设 PR 在 Service 中新增了宽泛的 catch (Throwable)。

规则：圈出异常捕获模式 → 上下文：拿附近代码 → AI：必要时取完整文件、查调用方 → 质检：检查报告遗漏和矛盾 → 结果：风险等级、文件、行号、理由及建议。

这是说明流程的假设例子，不是本次真实模型运行结果。规则命中也不代表一定存在业务缺陷。

和普通 LLM 调用有什么区别？

普通调用是“给材料 → 一次答案”。这里是“给材料 → 模型选工具 → Java 执行 → 工具结果写回 → 模型再判断”。主动选择工具并根据结果继续，是 Agent 的关键。项目手写循环，没有引入 Agent 框架。ReAct 不意味着代码获得了模型内部完整思维链。

怎样避免一直查资料？

默认主循环 8 轮；累计工具调用达到 4 次后，下轮不再提供工具定义。消息超过 64,000 字符预算的 80% 时压缩较长工具结果，仍超限就要求输出。达到轮数上限后还有一次强制输出调用；JSON 格式失败还可能重试。因此 8 轮不是整个请求最多 8 次模型调用，4 次也不是工具执行的严格硬上限。

Critic 是另一个模型吗？

它是另一个提示词角色，复用同一个 ModelProvider。检查幻觉、遗漏、严重度、重复、一致性；有问题触发一次修订，修订后不再复核。当前 Critic 只读规则风险和 AI 风险、建议，没有源码或工具轨迹，因此不能保证发现事实错误。

05 / 面试追问卡 · 点击看答法

把“用了什么”讲成“为什么这样做”

为什么同时用规则和 AI？

规则适合低成本发现固定模式，AI 适合理解上下文和解释影响。规则结果既进入 Prompt，也在最后合并，避免被模型漏掉。代价是规则误报也会被保留；后续可以引入规则置信度与证据复核。

9 条规则具体是什么？怎样扩展？

锁未释放、嵌套事务、宽泛 catch、异常吞噬或转换、SQL 拼接、硬编码密钥、不安全随机数、弱哈希、System.out.println。实现 RiskRule 并注册 @Component，Spring 注入 List<RiskRule>。检测器按适用类型执行，单条 scan 异常记录后跳过。适合用“策略接口 + 依赖注入”解释。

这是基于 patch 的启发式扫描，不能说成 AST、跨方法数据流或完整静态分析。

为什么要自己解析 diff？

后续规则、上下文切片都需要结构化行号。解析器从 hunk 头初始化新旧行号：新增只推进新行号，删除只推进旧行号，上下文两边都推进。得到统一数据结构，其他模块就不用重复解析文本。代价是需要自己维护异常 patch 和边界测试。

怎样控制 Token 与费用？

先按文件类型分组，复用组级指导；单文件 patch 默认限制 6,000 字符，用户材料预算 60,000 字符；Agent 会话还有轮次和字符预算。按需取资料减少不必要输入，但会增加网络与模型轮次。当前是字符近似控制，不能说成精确 Token 计费或绝对上下文硬限。

怎样减少幻觉？

提供规则与代码上下文，允许工具补证据，Prompt 要求引用具体代码、并发问题给执行时序，再用 Critic 检查结果一致性。这些是降低风险的手段；要证明改善，仍需标注 PR 集，对比误报、漏报与人工采纳率。

模型输出坏了怎么办？

先清理 Markdown 围栏并提取 JSON；语法解析失败，把错误反馈给模型，重试一次。仍失败尽量提取摘要，返回空 AI 风险与建议。最终合并仍可保留规则风险。注意这是格式失败的降级；模型 HTTP 失败不等于自动返回纯规则报告。现有解析也不等于严格 JSON Schema 验证。

限流和缓存如何设计？

RepositorySearchService 为 search_repo 提供进程内 ConcurrentHashMap，键为 owner/repo/query，命中缓存不消耗搜索次数。计数器按约 60 秒重置，超过 25 次拒绝。实际是简易计数窗口，不是严格滑动窗口。没有 TTL、容量上限、提交版本隔离；多实例也不共享限流。要扩展可以引入有界缓存及原子限流。

如果用户量上来，先改哪里？

先测量 GitHub 和模型各阶段耗时。当前请求串行等待，前端 120 秒超时，而模型单次配置 60 秒，多轮很容易超出前端等待时间。可改成异步任务返回 taskId，再轮询或 SSE 推送；之后根据指标增加并发限制、截止时间、幂等和结果缓存。这些是建议，当前未实现。

怎么验证这个项目有效？

现有测试覆盖 diff、分类、规则、上下文、Prompt、工具、Agent、复核、Pipeline 与接口错误，并使用 MockWebServer 模拟外部 HTTP。工程测试能验证流程，不能直接证明审查准确率。效果评估应使用人工标注的 PR，比较纯规则、单次 LLM、ReAct、ReAct + Critic，记录精确率、召回率、耗时与实际 Token 用量。

本次分层重构已运行后端完整测试，见逐类审查报告；测试使用外部服务替身，不代表线上审查准确率。

06 / 被追问时，真实最有说服力

这些边界，要能主动说清楚

以下是静态阅读代码发现的实现边界；分层重构已修复部分边界；其余按当前代码列明，未做线上联调。

大 PR 覆盖

抓文件只请求一页 per_page=100，未继续分页。缺失 patch 被当成无可分析内容，预算还会省略后续文件。

改进：分页、覆盖统计、显式“分析不完整”。

版本一致性

全文在原仓库按 head 分支名取，未固定 head SHA 与来源仓库。fork PR 可能取不到或取错版本。

改进：按 head.repo + head.sha 固定证据。

并发统计

已重构为 AgentReview 随本次调用返回轮次和工具次数；没有单例 last 字段。

已验证：并发交错请求各自保持统计。

配置层级

YAML 在 reviewpilot.ai.agent 下，代码读取 reviewpilot.agent。现有值恰好等于默认值，掩盖问题。

改进：统一层级，验证非默认配置生效。

复核证据不足

Critic 看不到源码，且把规则当权威；精确去重无法合并同义描述。修订已通过统一解析器保留 keyFindings。

已统一解析；仍需传递源码证据并评估误报。

资料预算不完整

8k 截断只用于预取风险文件；工具取全文路径未同样截断。初审也没有复用预取全文。

改进：统一上下文入口与全链路预算。
加分追问：Prompt 本身有什么问题？

系统提示词里有一句 “You are not a senior distributed-systems reviewer”，与后续角色定位冲突；严重度同时存在“需证明影响”“语义变化必须 HIGH”和基础设施例外。多套规则叠加可能导致判断不一致。下一步应收敛为统一标准，并用回归案例检验，而不是继续堆指令。

07 / 面试前最后一遍

用五分钟，讲完一条主线

  1. 0:00—0:40 用途：输入 PR 链接，输出定位到文件和行号的风险与建议。
  2. 0:40—1:40 架构：Vue → Spring Boot Pipeline → GitHub / DeepSeek → JSON 结果。
  3. 1:40—3:00 亮点：规则先圈疑点，Agent 主动补上下文，Critic 再检查。
  4. 3:00—4:00 取舍：准确性与成本、上下文完整度与预算、稳定规则与误报之间的平衡。
  5. 4:00—5:00 证据与改进：讲你真实完成的测试或案例，主动交代覆盖、并发和评估不足。
最值得记住的一句话：这个项目把“读改动、找证据、提意见、再复核”组织成了一条可控制的审查流程。
